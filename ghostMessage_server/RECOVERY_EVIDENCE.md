# 로그인 없는 계정 재연결: 구현 및 검증 근거

## 문제와 선택

GhostMessage는 로그인 없이 UUID와 8자리 보안 코드로 사용자를 식별한다. 보안 코드를 잃으면 계정을 복구할 수 없으며, 이 기능의 정확한 범위는 **이미 보관한 UUID와 코드로 다른 설치에서 계정을 다시 연결하는 것**이다.

기존 복구·메시지 작성·투표·삭제 요청은 보안 코드를 URL 쿼리에 넣어 전송했다. 이번 변경은 모두 `X-Security-Code` 헤더로 옮기고, 복구를 `POST /api/users/recover?uuid=...`로 바꿨다. 등록 응답에서 평문 코드를 한 번 전달하고 DB에는 BCrypt 해시만 저장하는 기존 구조와 레거시 평문 코드의 성공 시 해시 전환은 유지했다.

`UserService.recoverUser`와 `validateUser`는 동일한 UUID별 Redis 카운터를 사용한다. Lua 스크립트가 증가와 최초 900초 TTL 설정을 원자적으로 실행한다. 15분 동안 5회까지 코드를 검사하고 6회부터 HTTP 429를 반환한다. 성공하면 카운터를 삭제한다. 작성·투표·삭제도 같은 검증을 거치므로 복구 엔드포인트만 우회해 코드를 추측하는 경로를 남기지 않았다.

## 검증 결과 (2026-10-18, 격리된 로컬 PostgreSQL 15·Redis 7)

- `UserServiceTest`: 기존 검증 4건과 복구 성공·잘못된 코드·제한 초과 3건, 총 **7/7 통과** (`./gradlew test --tests com.ghostMessage.service.UserServiceTest`).
- 실제 HTTP/Redis: 새 계정의 잘못된 코드 5회는 모두 **401**, 6번째의 올바른 코드는 **429**, Redis 키 TTL은 **899초**였다. 다른 새 계정의 올바른 코드 복구는 **200**, 헤더 누락은 **401**이었다.
- 확장 프로그램 Origin의 `POST /api/users/recover` CORS 사전 요청은 **200**, `Access-Control-Allow-Headers: x-security-code`였다.
- `node --check`로 `extensions/background.js`와 `extensions/options.js` 구문을 확인했다. 저장소 검색에서 더 이상 `securityCode=` 쿼리 전송은 발견되지 않았다. 확장 프로그램의 API 호스트 권한도 명시했다.

## 포트폴리오에서 주장할 범위

**문제:** 로그인 없는 익명 사용자가 기기를 바꿀 때 식별 정보를 다시 연결해야 했지만, 보안 코드가 URL에 실리고 시도 제한이 없었다.

**해결:** UUID+보안 코드 재연결은 유지하며 코드를 헤더로 이동했다. Redis에 UUID별 5회/15분 제한을 원자적으로 기록하고, 성공 시 해제했다. 같은 제한을 모든 코드 검증 경로에 적용했다.

**검증:** 서비스 테스트 7/7 통과, 실제 HTTP에서 5회 401·6회 429·정상 복구 200과 확장 프로그램 CORS 허용을 확인했다.

## 남은 조건

- 이 제한은 UUID별이며 IP별/전체 요청 제한은 아니다. 알려진 UUID에 제3자가 5회 실패하면 정당 사용자도 남은 제한 시간 동안 차단될 수 있다. Redis의 `allkeys-lru`가 제한 키를 메모리 압박 시 제거할 수 있어 **강한 보안 보증으로 표현하면 안 된다**. Redis 장애 시 검증은 성공하지 않고 오류로 종료된다.
- URL 노출 경로는 제거했지만 보안 코드 자체나 확장 프로그램 로컬 저장소를 별도로 암호화한 것은 아니다. HTTPS와 클라이언트 저장소 보호가 계속 필요하다.
- 서버는 구버전 쿼리 인증을 더 이상 받지 않는다. **기존 설치 확장 프로그램은 서버를 먼저 배포하면 작성·투표·삭제·복구가 중단된다.** 운영 반영 전 확장 프로그램 배포/호환 기간을 결정해야 한다. 이번 변경은 로컬에서만 검증했으며 운영 배포하지 않았다.
